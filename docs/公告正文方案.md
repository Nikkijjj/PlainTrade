## 二、PDF 处理的几种路线（含 agent 生态常见做法）

| 路线 | 代表库 | 优点 | 缺点 | 对我们 |
|---|---|---|---|---|
| **直接抽文字层** | **PyMuPDF(fitz)** | 最快（143 页/秒级）、中文好、本机已有 | 不还原表格结构 | ✅ **主路线** |
| 表格感知 | pdfplumber | 能把三表抽成二维 | 慢 5-10× | ✅ **只对财务页兜底** |
| 纯 Python 解析 | pdfminer.six | 无二进制依赖 | 慢 | ⚪ 备选 |
| 版面模型 | Docling / MinerU / Marker | 保留标题层级、表格、阅读顺序，质量最好 | **要下模型（数百 MB～GB）+ 常需 GPU** | ❌ 装包困难，不选 |
| 全家桶 RAG | Unstructured / LlamaIndex / RAGFlow | 开箱即用、自带切块与向量库 | 重、黑盒、依赖多；评估不可复现 | ❌ 不选 |
| OCR | PaddleOCR / Tesseract | 能读扫描件 | 要装模型、慢 | ⚪ 仅"抽不出文字"时兜底 |
| 多模态大模型 | GPT-4o / DeepSeek-VL | 什么都能读 | 贵、慢、不可复现 | ❌ 不用 |

**为什么不上 layout 模型 / RAG 全家桶**（这是关键取舍）：

1. 我们只处理**一种文档**（A 股定期报告），章节结构极其固定，**正则切章节比模型更可控**
2. 模型要下载几百 MB～GB，本组装包都困难（pip 镜像反复超时）
3. 评估要**可复现**：同一份 PDF 两次跑必须得到同样的 chunk；带模型的方案做不到
4. 15 天、3 个人，**没有余量调试模型推理**

**什么时候才值得上重型方案**：文档类型杂（合同/研报/票据混在一起）、需要跨页表格还原、或要做多模态问答。我们都不是。

## 二之二、参照生产级 PDF-RAG 方案：采什么、不采什么

> 参照 [Agent-RAG 处理复杂 PDF：从 Demo 走向生产级](https://jishuzhan.net/article/2095305972093472769)（四层架构）。
> 我们的约束是 15 天 / 3 人 / 无 GPU / 装包困难 / 评估要可复现，所以逐层做了取舍。

| 文章的层 | 做法 | 我们的决定 | 理由 |
|---|---|---|---|
| 1 | 文档类型动态判别（原生文本 vs 扫描件） | ✅ **采** | 抽样前 3 页算字符/页，<50 判扫描件并标记降级 |
| 1 | 多模态模型把页面当图像解析 | ❌ **不采** | 见下三条 |
| 1 | 按页向量化 / 页级 Embedding | ❌ 向量库不采　✅ **页码必须存** | 349 篇规模 BM25 够；向量召回受模型版本影响，评估不可复现 |
| 2 | 结构还原 + 元数据（页码/标题层级/章节/表格编号） | ✅ **全采** | 新增 `doc_meta` 表，chunk 带 `page` / `section` / `kind` |
| 3 | 语义切片 + **Chunk Context Injection** | ✅ **全采**（原方案漏了这条） | 把文档/章节/页码写进 chunk 正文前缀 |
| 4 | Agent 工具链按需加载（Read_Page / Extract_Table） | ✅ **采** | 新增 `search_chunks` / `read_pages` 工具，永不把全文灌 prompt |
| 4 | 幻觉三条红线（强制溯源 / 证据不足要说没找到 / 评测校验） | ✅ **全采** | 已有雏形（evidence 引用 / `no_view` / 越界拦截），补"数值一致性"评测 |
| 4 | Analyze_Chart（理解 PDF 里的图表） | ❌ 不采 | 我们的图是**自己渲染的 PNG**，不需要理解别人的图 |

### 为什么不用多模态解析 PDF（三条硬理由）

**① 我们要"可核验的原文"，VLM 给的是"转述"**

这是最关键的。项目核心主张是**不失真**：文字层抽取出的是 PDF 里的原始字符，可以逐字核对；
多模态模型输出的是"理解后的复述"，它可能把"同比下降 3%"写成"下降约 3%"，
而我们的保真度评估正是建立在这类差异上。**用 VLM 解析等于在证据链第一环引入不可核验环节。**

**② 实测证明不需要**

茅台 2024 年报 143 页，`fitz` 抽出 **176,089 字** —— 说明 A 股 2023–2025 定期报告有完整文字层。

**③ 成本与确定性**

VLM 解析 143 页要几十次调用、几分钟、几块钱，且**同一份 PDF 两次结果可能不同**。
而我们的 chunk 必须确定性（验收里写了"重跑一次 chunk 数完全一致"）。

### 我们额外加的（文章没强调，但对本项目必要）

| 加的东西 | 为什么 |
|---|---|
| `doc_meta.pdf_sha256` | 同一份 PDF 重下要能确认是同一份；也是"解析可复现"的锚 |
| `chunk.kind = table` | 表格单独成块，检索"净利润"时不会把表头数字串成一句话 |
| **数值一致性校验** | 从 PDF 抽的营收/净利润与 `financials` 表对账（±0.5%），这是最硬的防幻觉手段 |
| 扫描件**不做 OCR** | 只标记 `no_text_layer` 并降级到标题 —— OCR 要装模型，且对 3 年年报没必要 |

## 三、我们的方案（分四层，每层都能单独停）

```
巨潮 query ──→ PDF 下载 ──→ 解析(文字层 + 表格兜底) ──→ 章节切块 ──→ 入库 + chunk 级 FTS
   (元数据)      (限流礼貌)      (fitz/pdfplumber)        (正则)         (可引用到页)
```

### 3.1 按价值分四层，只补 T1+T2（349 条）

> 修正：「其他」2,597 条**不是全都该放弃** —— 实测分类后发现里面混着高价值公告。

| 层 | 内容 | 条数 | 处理 |
|---|---|---|---|
| **T1** | 年报正文 30 + 半年报 44 + 季报 50 + 分红 72 | **196** | ✅ 补全文 |
| **T2** | 重大事项 + 增减持/质押 + 业绩预告 | **~130** | ✅ 补全文 |
| T3 | 股权激励 / 回购 | 342 | ⚪ 只保留标题（回购标题已含"回购"） |
| **T4** | 程序性决议 700 + H股 326 + 法律意见 156 + 章程 135 + 未归类 808 | **~2,125** | ❌ 放弃正文 |

**2,597 条的实际构成（实测；注意 `doc_type` 字段不可靠，以标题关键词重判为准）**：

| 分组 | 条数 | 价值 |
|---|---|---|

| 股权激励 / 回购 | 342 | 中低 |
| H股 / 境外披露 | 326 | 极低（港交所格式表） |
| 法律意见 / 核查意见 | 156 | 极低（多为附件，无正文） |
| 章程 / 制度 | 135 | 极低 |
| **重大事项**（诉讼/处罚/停牌/关联交易） | **65** | **高** |
| **增减持 / 质押** | **32** | **高** |
| 分红相关 | 17 | 高（已被 T1 覆盖） |
| **业绩预告 / 快报** | **16** | **高** |

**为什么放弃 T4 的 ~2,125 条**：

1. **内容形态是套话**：律师意见、章程条款、股东大会程序，对"这只股票怎么样"零信息量
2. **很多根本没有正文**：实测有 43 字、45 字的正文，都是这类附件型公告
3. **成本悬殊**：2,125 条 × 3.6 MB ≈ **7.6 GB 流量**，几小时机时，收益接近 0

**关键：放弃的是「正文」，不是「公告」** —— 标题全在库里，所以这 2,125 条依然：

- ✅ 可检索（FTS 索引标题）
- ✅ 可引用（`Evidence.quote` 填标题）
- ✅ 能出现在"3 条依据"里
- ❌ 不能引用原文细节（这类公告也不需要）

像"控股股东增持计划实施完成"这类，**标题本身就把信息给全了**。

### 3.2 存储设计（新增两处）

```sql
-- ① 公告表补解析元数据
ALTER TABLE announcements ADD COLUMN pdf_url TEXT;
ALTER TABLE announcements ADD COLUMN page_count INTEGER;
ALTER TABLE announcements ADD COLUMN parse_status TEXT;   -- ok | no_text_layer | failed | title_only

-- ② 文档级元数据（生产级 PDF-RAG 的第 2 层：元数据才是可追溯的关键）
CREATE TABLE IF NOT EXISTS doc_meta (
  doc_id      TEXT PRIMARY KEY,   -- announcements.art_code
  company     TEXT, report_period TEXT, publish_date TEXT,
  pdf_url     TEXT, page_count INTEGER, pdf_sha256 TEXT,
  parser      TEXT,               -- fitz | pdfplumber | none
  parse_status TEXT               -- ok | no_text_layer | failed
);

-- ③ 新增 chunk 表（检索与引用都基于它）
CREATE TABLE IF NOT EXISTS doc_chunks (
  doc_id  TEXT NOT NULL,      -- announcements.art_code
  seq     INTEGER NOT NULL,   -- 第几块
  page    INTEGER,            -- 起始页（引用用："第 37 页"）
  section TEXT,               -- 章节名（"经营情况讨论与分析"）
  kind    TEXT DEFAULT 'text',-- text | table（表格单独成块）
  text    TEXT NOT NULL,      -- ★ 已注入上下文的文本，见下
  PRIMARY KEY (doc_id, seq)
);
CREATE VIRTUAL TABLE IF NOT EXISTS chunks_fts USING fts5(
  doc_id UNINDEXED, page UNINDEXED, section, text, tokenize='unicode61'
);
```

**为什么 chunk 级而不是整篇**：一份年报 176k 字，整篇入索引会有两个问题 ——
① BM25 打分被长文档稀释，命中精度下降；② 无法告诉用户"在哪一页"。
切成 ~800 字的块、带页码和章节名，检索结果就能直接引用到"《2024 年报》第 37 页 · 经营情况讨论与分析"。

#### Chunk Context Injection（片段上下文注入）

参照生产级 PDF-RAG 的做法：**上下文不只放在字段里，要写进 chunk 正文**。

```python
# 入库时拼前缀（split 时生成，检索时原样返回）
prefix = f"【{company}·{report_period}·{section}·第{page}页】"
chunk_text = prefix + body
```

| 好处 | 说明 |
|---|---|
| 检索更准 | "管理层怎么解释增速下滑"能命中「管理层讨论」块，而不是利润表附注 |
| LLM 不迷失 | 模型拿到片段就知道"这是谁的哪一年哪一节"，不用再猜 |
| 引用可核验 | 前缀本身就是引用信息，`Evidence.quote` 直接可用 |

**代价**：每块多 ~20 字，检索时会造成轻微词频偏移（可忽略）。

### 3.3 解析策略（三步递进，任一步失败就降级）

| 步 | 做法 | 失败时 |
|---|---|---|
| 1 | `fitz` 抽全文文字层 | 若单页平均字符 < 50 → 判为**扫描件**，`parse_status=no_text_layer`，不索引，只用标题 |
| 2 | 按章节正则切块（见 3.4） | 切不出章节 → 退化为"按页切块" |
| 3 | 对「主要会计数据」附近页用 `pdfplumber` 抽表 → Markdown | 抽表失败 → 该块只用纯文本。**此步只做抽查**：数字的真值已在 `financials`，PDF 抽数字不是验收门槛 |

### 3.4 章节正则（A 股定期报告结构固定，实测有效）

```
重要提示 / 第一节 重要提示
第二节 公司简介和主要财务指标
第三节 管理层讨论与分析（或"经营情况讨论与分析"）
第四节 公司治理
第五节 环境与社会责任
第六节 重要事项
第七节 股份变动及股东情况
第八节 优先股 / 债券
第九节 财务报告（含审计报告）
```

切块规则：**章节内超过 800 字再按段落切开**，避免出现 3 万字一块。

### 3.5 限流与礼貌（保护自己也保护别人）

| 参数 | 值 | 理由 |
|---|---|---|
| 并发 | **1**（串行） | 不做并发爬取 |
| 请求间隔 | **2 秒** | 未知容忍度，先保守；实测可调 |
| PDF 大小上限 | 20 MB | 超过则跳过并标记 failed |
| 超时 | 60 秒 | 大 PDF 下载慢 |
| 重试 | 1 次（退避 3 秒） | 不做长重试链 |
| 单批 | **50 篇** | 先跑 5 篇验容忍度，再放量 |

### 3.5b 章节抽取（替代"前 40 页截断"）

年报里**数字章节（财务报告/审计报告）与 `financials` 重复**，价值在**定性章节**。
所以不按页数截断，按章节取舍：

| 章节 | 处理 | 理由 |
|---|---|---|
| 管理层讨论与分析 | ✅ **全文保留** | 唯一的定性分析（增速下滑的原因等） |
| 重要事项（诉讼/担保/风险） | ✅ **全文保留** | 风险提示，对"这只怎么样"最有价值 |
| 公司简介和主要财务指标 | ⚪ 只留文字，数字不抽 | 数字已由 `financials` 精确提供 |
| 重要提示 | ⚪ 前 500 字 | 多为套话 |
| 财务报告 + 审计报告 | ❌ **丢弃** | 几十页纯数字与表格，全是冗余 |
| 公司治理 / 股东情况 | ❌ 丢弃 | 与结论无关 |

**收益**：单篇正文从 ~6 万字降到 ~1.5 万字，且更聚焦。

### 3.6 体积预算

| 项 | 估算 |
|---|---|
| 219 条 × 平均 3 万字 | ≈ 6.5M 字 ≈ **13 MB** |
| 截断策略：单篇只存前 **60,000 字**（约 40 页） | ≈ **4 MB** |
| chunk 冗余（切块后约同量） | +4 MB |
| **DB 从 6 MB → 约 14 MB** | 可接受 |

> 只存前 60k 字是刻意的：年报前 40 页已含"重要提示 + 主要财务指标 + 管理层讨论"，
> 这三块覆盖了小白要看的 90%。财务报表附注（几百页）对我们是噪音。
> 原 PDF **不入库**（3.6MB × 219 = 800MB，太大），需要时按 `pdf_url` 重下。
