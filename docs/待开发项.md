## 三、分工

### 分工原则

1. **按目录分，不按功能分** —— 三个人同时改同一文件必然冲突
2. **接口先行** —— `contracts/` 已冻结，谁都不许改；要改必须三人当面同意并升 `schema_version`
3. **fixtures 是解耦器** —— `cases/fixtures/` 里的 4 份样例让 C、A 不用等 B
4. **每天至少合并一次**

### A —— 数据与评估（`data/` `research/` `eval/` `cases/`）

| 优先 | 任务 | 说明 |
|---|---|---|
| ① | **D-13 公告正文补齐** | 挂后台分批跑，不占人力；**今天就能开始** |

**A 是"数据守护者"**：`cases/fixtures/` 只有 A 能改，别人需要新样例找 A 加。

## 九、Git 协作流程（三人都按这个来）

### 9.1 分支模型

| 分支 | 用途 | 谁推 |
|---|---|---|
| `main` | **稳定基线**，只接收合并进来的 PR | 谁都不直接推 |
| `nikki` / `linda` / `silence` | 每人一条长期工作分支 | 本人 |
| （可选）`feat/d01-xxx` | 单个功能太大时从自己的分支再开短分支 | 本人 |

`main` 建议在 GitHub 仓库设置里加保护：`Settings → Branches → Add rule`，勾选 *Require a pull request before merging*。
这样"不小心直接推到 main"就从物理上不可能了。

### 9.2 每天 4 步

```bash
# ① 开工前同步（先拉自己的，再把 main 的更新合进来）
git switch nikki
git pull
git merge origin/main

# ② 改代码
#    ...

# ③ 提交（提交信息带待开发项编号）
git add -A
git commit -m "feat(D-01): 实现 llm.client.complete"

# ④ 推到自己的分支
git push
```

> 为什么不 `git pull --rebase`：我们三人各占一条长期分支，merge 更不容易把别人搞乱。
> 只有在自己分支上、还没 push 时，用 rebase 整理提交才安全。

### 9.3 提交信息规范

`类型(编号): 摘要`

| 类型 | 用在哪 | 例子 |
|---|---|---|
| `feat` | 新功能 | `feat(D-02): manager.decide 产出 ArgDoc` |

### 9.6 三个坑（都会真的发生）

**① 二进制数据库无法合并 —— 只能一个人提交**

`data_files/plantrade.db` 是二进制，git 没有"合并"这个选项，两个人各推一次必冲突且无解。

规则：
- **只有 A 负责提交数据库**，其他人不提交
- 别人本地重建库后，`git status` 会显示它被修改 —— **不要提交，直接丢弃**：

```bash
git restore data_files/plantrade.db
```

**② 分支别放太久**

长期分支放两周不合并，最后一次 merge 会变成灾难。**每天 merge 一次 `main`** 就能避免。
以我们按目录分工（A 改 `data/`、B 改 `agents/`、C 改 `adapt/`）的情况，冲突本来就少。

**③ `contracts/` 是唯一的高危区**

PR 里只要出现 `contracts/` 的改动，**必须三人确认**并升 `schema_version`。
它是唯一会同时打坏另外两人代码的地方 —— 字段改名不会报错，只会让别人的功能静默失效。

### 9.7 冲突怎么处理

| 场景 | 做法 |
|---|---|
| 两人改了同一文件的不同位置 | git 通常能自动合并，确认后 `git add` + `git commit` |
| 两人改了同一行 | 谁先开 PR 谁的版本保留，另一个改成适配 |
| 冲突在 `contracts/` | **停下来**，三人当面 5 分钟定字段，然后两人一起改 |
| 冲突在 `data_files/*.db` | 别解决 —— `git restore` 丢弃本地，用仓库里的 |
