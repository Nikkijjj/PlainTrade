## 三、分工

### 分工原则

1. **按目录分，不按功能分** —— 三个人同时改同一文件必然冲突
2. **接口先行** —— `contracts/` 已冻结，谁都不许改；要改必须三人当面同意并升 `schema_version`
3. **fixtures 是解耦器** —— `cases/fixtures/` 里的 4 份样例让 C、A 不用等 B
4. **每天至少合并一次**

### A —— 数据与评估（`data/` `research/` `eval/` `cases/`）

| 优先 | 任务 | 说明 |
|---|---|---|
| ① | **D-13 公告正文补齐** | 挂后台分批跑，不占人力；**今天就能开始** |
| ② | **D-14 板块补齐** | 等接口限流解除（30–60 分钟），一条命令 |
| ③ | **D-15 五个指标** | 吃 fixtures 开发，不用等 B |
| ④ | **D-16 批量跑** | 依赖 D-15 |
| ⑤ | **D-17 演示案例** | 等 D-03 通了才能跑真链 |
| ⑥ | D-18 exe 打包 | **务必在 P1 中段试打一次**，别留到最后 |

**A 是"数据守护者"**：`cases/fixtures/` 只有 A 能改，别人需要新样例找 A 加。
**A 还是备份**：B 或 C 掉线时，A 接手（A 的工作最不容易被阻塞）。

### B —— agent 引擎（`agents/` `pipeline/` `llm/`）

| 优先 | 任务 | 说明 |
|---|---|---|
| ① | **D-01 `llm/client.py`** | **30 行，全项目唯一的单点阻塞。开工第一件事** |
| ② | **D-02 `manager.decide`** | 先返回"假但合法"的 ArgDoc（stance=no_view）把链路打通，再逐步变真 |
| ③ | **D-03 `pipeline.run`** | 打通后 C 才能接真数据、A 才能跑评估 |
| ④ | D-06 三分析师 | 每个至少 3 轮 prompt 迭代 |
| ⑤ | D-07 辩论 | 加分项，最后做 |

**B 的坑**：`manager` 最容易写出"正确的废话"。**验收标准不是"读起来像分析师"，而是"证据不足时会说 no_view"**。

### C —— 适配与界面（`adapt/` `ui/` `guardrails/` `frontend/`）

| 优先 | 任务 | 说明 |
|---|---|---|
| ① | **D-04 + D-05** | 纯函数，用 fixtures 就能做，**第一天就能并行** |
| ② | **D-08 术语门控** | 最费时，建议早开始；**先把 config/jargon.json 从 5 条扩到 ≥20 条**，再写改写 |
| ③ | D-09 + D-11 | 都是纯函数 |
| ④ | **D-10 图表渲染** | 中文字体坑已踩过（见数据文档），复用 `scripts/make_mock_images.py` 的画法 |
| ⑤ | **D-12 前端接真数据** | 依赖 D-03 |
| ⑥ | D-19 / D-20 / D-21 | 加分项 |

**C 的坑**：`adapt/` 是**纯函数层**，不许读写文件/数据库、不许调 LLM 客户端（除 `termgate` 允许调 `llm` 做改写）。保持纯函数才好单测。

## 六、DoD（完成定义）

一个待开发项算"完成"，必须同时满足：

- [ ] 函数体不再是 `raise NotImplementedError`
- [ ] 有**至少 1 条**单测（`tests/` 下），且 `pytest` 全绿
- [ ] 失败路径有处理（返回 `ToolResult(ok=False)` 或降级，不抛裸异常）
- [ ] 不违反依赖矩阵（`check_structure` 通过）
- [ ] 文件 ≤200 行（超了拆模块，不是加豁免）
- [ ] 提交信息写明编号，如 `feat(D-04): adapt.summarize 四档置信度`
- [ ] 在本文档把该行状态改为 ✅ 并填实际耗时
